# Agent 笔记：工程作业的持久确认与恢复

状态：已实现

## 先说结论

客户端通过项目 API 发起一次仓库测试，中控和节点用同一个作业编号记录整个执行。连接中断后，节点从本地账本取出原结果回传。若节点曾接单、进程退出时没有写下终态，中控显示“待核实”，值班人员先检查执行证据。

## 问题

测试可能已经完成，确认消息却因网络断开而丢失。此时新建一项同参数作业会再次运行测试，所得结果属于另一次执行。多个中控进程先后持有同一节点连接时，也需要知道谁有权处理当前回执。

## 决策

中控在 MySQL 保存项目、发起人、请求号、作业号、节点和固定提交。节点在已认证的 WebSocket 长连接上声明能力，中控派发前复核项目授权和节点分配。节点先将参数与接单状态同步到磁盘，再在隔离环境执行管理员登记的测试入口。同一作业和参数再次到达时，返回已有进度或终态。同一编号的参数有变化时拒绝执行。

中控持久化最终结果后确认收讫，节点重连时继续对账。例如运维看到成功回执丢失，应查询原作业号的日志和真实退出码。另行点击“启动测试”会产生新的执行记录。旧终端与模板命令继续使用各自协议。节点永久离线时，中控按作业截止（30 分钟）加 5 分钟宽限的定时扫描把仍未收敛的 dispatched/running/cancelling 作业落为 `uncertain` 终态（`next()` 依赖目标节点的活会话，此前这类作业会永久滞留并堵塞节点串行队列）；节点回归后的真实回执仍可覆盖核实（2026-11-16 补充，V52 索引支撑扫描）。

## 考虑过的备选方案

直接在终端重发命令实现简单，但远端无法据此辨认此前是否完成。消息队列的消费确认证明消费者收到消息，不能回答哪个 Git 提交实际执行、进程怎样退出。

## 后果

中控重启后仍可取得同一次测试的结果。节点为此需要持久、可写且由单一 Agent 占用的账本卷。账本损坏时停止执行。人工删除在线账本会破坏去重依据。发布另有按版本与服务记录的执行器，未知外部效果需要按对应执行器的事实核实。

## 验证

此前的 V50 双机验收由浏览器提交固定版本，丢弃终态确认并终止首个中控 JVM。第二个 JVM 接管后，观察到三次相同终态、三个日志分段、一个执行标记和退出码 0。此证据针对同一块节点账本上的仓库测试。[双机实测](../../../../docs/logs/20261112-中控跨JVM作业接管.md)
