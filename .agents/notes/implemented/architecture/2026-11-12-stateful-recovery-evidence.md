# Agent 笔记：有状态数据恢复到独立实例并核验业务

状态：已实现

## 先说结论

备份生成后，工具先在独立实例或新目录中恢复，再用业务读取、写入或身份抽样证明能用。中控和业务中间件的恢复材料分别管理。每次演练记录所用版本、拓扑、实际恢复位置和耗时，切换现网连接由负责人另行决定。

## 问题

校验文件可读只能发现部分损坏。数据库角色可能无法登录，Redis 键值的剩余有效期可能偏离业务约定，RabbitMQ 队列定义齐全时仍可能缺少未消费消息。中控的数据库恢复后，也可能缺少解密历史凭据的密钥或真正的制品文件。

## 决策

PostgreSQL 逻辑恢复验证角色、约束和订单读写。物理恢复将基础备份与连续的预写日志（WAL）配套保管，按命名恢复点回放到新实例，核对实际日志位置及该点前后的两笔事务。

Redis 缓存实例验证应用回源和重新填充，持久实例验证恢复后的键、剩余有效期和再次重启。RabbitMQ 分开验收交换机、队列、权限的恢复，以及带业务 ID 的重投和消费去重。导出的 definitions 保存消息拓扑配置，恢复原队列内容需要独立的数据或业务重放来源。

中控快照加密封存一致性 MySQL 导出、环境及文件型密钥和数据库引用的不可变制品。恢复先校验对象，再导入新库、新目录，核对节点凭据、密钥解密和制品摘要。恢复模式暂停新派发，值班人员核对快照之后的撤权与节点实际结果，再决定开放入口。

## 考虑过的备选方案

覆盖源实例会让一次错误恢复同时破坏原始数据与调查依据。把三种中间件都按“导出成功”验收，会遗漏缓存回源、消息重复处理和已提交事务的恢复边界。

## 后果

独立目标保留源实例，可用真实应用语义检查恢复。代价是额外的存储、计算和密钥保管。以下证据适用于各自版本、测试数据量及拓扑，企业的跨机灾难恢复和生产规模恢复时间仍须单独测量。

## 验证

PostgreSQL 18.6 演练中，源有订单 301、302，第二笔之后的 WAL 也已归档。新实例实际重放到命名点 `0/40071E0`，仅包含 301。目标新增 303 后源库不变。V50 候选 JAR 的中控恢复演练在 MySQL 8.4.9 核对了节点、文件型密钥和 1,350,000 字节制品。被篡改的对象在创建新数据库前即遭拒绝。[中间件实测](../../../../deploy/middleware/verification.md) · [中控恢复实测](../../../../deploy/recovery/README.md)

从仓库根复现下列演练。第一条使用 Linux、Docker Compose 和已拉取的同摘要镜像。第二条使用有权限启动临时 MySQL 的测试账号、独立临时目录及真实候选 JAR。企业恢复手册给出密钥保管及暂停派发要求。

```sh
python3 deploy/middleware/pitr_smoke.py --image postgres@sha256:10a5c69a83035ab5239f5620d708520e8b28f5aa1f2b20143e6024532edadfb5
python3 deploy/recovery/smoke.py --server-jar /path/to/candidate.jar --mysql-bin /opt/mysql-8.4/bin --scratch /path/to/private-scratch
```
