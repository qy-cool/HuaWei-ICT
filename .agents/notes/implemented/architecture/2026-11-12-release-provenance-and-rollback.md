# Agent 笔记：构建来源、跨环境发布与应用回滚

状态：已实现

## 先说结论

测试和生产使用同一份带摘要的制品。生产部署要求制品来自已登记的构建节点，并已在该服务的测试环境健康发布。回滚以新的发布代次切回上一健康版本，生产请求和已发生的业务事务保留各自记录。

## 问题

同一提交重新打包可能得到不同字节，登记人关联一个成功的测试作业也不能证明所上传的文件由该作业生成。部署后已有订单继续变化，遇到坏版本时直接恢复整库会抹去发布后的合法交易。

## 决策

可信节点从本次隔离构建收集输出。中控核对项目、作业、来源节点和固定提交，将制品按 SHA-256 摘要寻址。人工上传的来源单独显示，可用于测试环境核查。生产提升要求构建节点来源和对应服务的测试健康记录。执行器在目标节点核对内容摘要及独立签名，运行候选探针，并持久化实际结果供重送。

按项目、环境、服务串行分配发布代次，分别记录目标节点与上一健康发布。失败时恢复原活动版本，恢复结果无法证实时标记待核实。应用回滚通过常规发布路径执行，业务数据的修复另有独立的恢复记录。

## 考虑过的备选方案

为每个环境重建一次可以嵌入不同配置，但生产字节与测试样本会发生分歧。仅登记上传操作者和源码 SHA 会把人工替换文件误认为节点生成的同一制品。应用异常时恢复整库虽然能还原旧结构，却可能同时丢失后续订单。

## 后果

发布审查可以回查作业、字节、目标和实际健康回执。企业需要维护可信构建环境、签名密钥和健康探针。已有证据覆盖签名静态站点的真实切换。Java 长进程与消息消费者交接、跨物理节点滚动切流及业务数据库兼容性需要各自的运行证据。

## 验证

V50 双机实测从 ARM64 节点收集 10,240 字节静态包，首次上传确认丢失后仍返回同一制品 ID。相同制品成功由测试提升到生产，人工上传包即使在测试环境健康，进入生产时也返回 409。坏候选回到原活动页，显式回滚产生新代次。[签名发布及回滚实测](../../../../docs/logs/20261112-签名静态制品发布双机验收.md)

从仓库根执行，使用专用中控、节点、候选 JAR 与目标架构 Agent，运行机备齐 Python 验收依赖。两个逻辑环境可共用一台物理开发机，记录验收时的真实拓扑。

```sh
python scripts/api-test/run-project-jobs-e2e.py --central CENTRAL_ALIAS --worker WORKER_ALIAS --jar PATH_TO_SERVER_JAR --agent PATH_TO_LINUX_AGENT --releases
```
