# 签名静态制品发布双机验收

## V50 构建节点来源、签名提升和回滚

2026-11-12 对包含生产制品来源检查的候选中控执行 `--releases`，空库实际迁移至 V50。中控位于 x86_64 Linux，构建、测试及生产服务由同一台 ARM64 机器上的两个独立节点身份承载。中控使用专用 MySQL 8.4.10，测试对象为静态站点。

1. ARM64 节点报告 linux/arm64、CPU、已登记 orders 仓库及 git、tar。节点在隔离环境从指定 commit 生成 10,240 字节 tar，由正式上传器上报。丢弃第一次成功上传的响应，再执行上传器，两次返回同一制品 ID。项目目录只有一条制品记录，下载的摘要、来源节点、作业 ID、提交及归档内页面内容一致。
2. 验收运行机从中控回读上述真实制品，计算 SHA-256 并签署 RSA 分离签名。通过 HTTPS 让测试节点执行签名及业务探针校验，然后将相同制品 ID 提升到生产，两个环境的实际活动页面均为 v1。首次测试健康回执已经入库后被代理丢弃，节点重放原始结果，审计记录未重复。
3. 人工上传 v2 并通过测试环境业务探针后，对其发起生产发布得到 HTTP 409。随后测试环境尝试一个业务探针失败的候选包，活动页面恢复到 v2。显式回滚重新获得独立代次，实际页面回到最初由节点构建的 v1。
4. 此轮共五条发布记录，两个逻辑环境，一个物理开发/应用节点。作业出现两次等值终态送达，只有一次真实执行标记，三个日志分段，退出码为 0。两个临时夹具均等待进程退出，随后检查远程目录已删除。浏览器和双 JVM 部分另见[中控跨 JVM 作业接管验收](20261112-中控跨JVM作业接管.md)。

本轮候选 JAR SHA-256 为 `0fb637ca91bab82e0fdfe187ea30ff0b78edaaf9e48b9389f65f25f5f3120e14`，ARM64 Agent SHA-256 为 `4c2f518142f528e086781f7a2d5276cba6acd50a4600c525938e138cf11eb463`。生产密钥托管、组织级真实签名人、数据库回滚和多物理节点滚动切流尚需在相应环境实测。

## V43 初次发布回归

2026-11-12，在一台 x86_64 Linux 云中控和一台 ARM64 Linux 内网机器完成双机测试。中控从空 MySQL 8.4.10 数据目录迁移到 V43。ARM 机上两个独立节点身份分别分配到测试和生产环境，每个身份使用自己的活动版本目录。节点使用临时 CA 验证中控 HTTPS，执行器以非 root 身份检查 RSA 分离签名、SHA-256 和回环 HTTP 业务探针。

| 操作 | 实际结果 |
|---|---|
| 从正常用户入口创建作业、重复提交并丢弃第一次终态确认 | 1 次实际测试，2 个连接，2 次结果送达，3 段日志和 1 个执行标记 |
| 将测试作业关联至三份独立构造的签名 tar，重复上传 v1 | 同一摘要、作业和类型得到同一制品 ID。制品由验收程序构造和上传，保留提交者与成功作业关联 |
| 测试环境发布 v1，首次健康回执已经提交后将响应改为 503 | 执行器从持久记录重放，审计仅各记 1 次排队、认领和健康。实际活动页面内容为 v1 |
| 将同一制品 ID 提升生产 | 两个环境记录的 SHA-256 相同，生产活动页面为 v1 |
| 测试环境升级 v2，再发布业务探针失败的包 | v2 实际就绪，坏包标记失败，活动目录及探针回到 v2 |
| 申请回滚至 v1 | 新发布代次获得节点健康回执，活动页面重新提供 v1 |
