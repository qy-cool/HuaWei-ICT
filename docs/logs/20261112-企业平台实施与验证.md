## 交付边界与下一轮验收

**最终纯后端回归。** 使用本轮 JAR、ARM64 Agent，以及参数 `--capture-build --failover --releases`。空 MySQL 迁移到 V50，API 完成注册、登录、项目与一次性节点登记。首个 JVM 被强制终止后，第二个 JVM 接回同一节点。观察到两次连接、三次等值终态、三段日志、一次实际执行及退出码 0。10,240 字节制品上传两次，只有一个 ID；五次发布覆盖同摘要提升、拒绝人工制品进入生产、坏版本恢复至 v2 及显式回滚至 v1。两个环境位于同一物理 ARM 节点。两机临时进程和目录均已清理。独立 API 测试夹具通过显式设置临时制品目录运行；正式 systemd 安装使用私有持久目录。[复跑程序](../../scripts/api-test/run-project-jobs-e2e.py)

本次业务交付为后端与工具；此前使用临时浏览器客户端的项目操作记录作为历史测试保留，管理台与业务前端框架由负责人自行决定。独立的 code-server 验收用于验证工作区后端。安装入口也做了独立验证。在无宿主挂载的 Linux 容器内执行真实安装脚本，首次配置与目录权限正确、占位配置保留时只装载单元；填写后发出启动指令，活动服务换版时发出重启指令，同名不同字节的版本被拒绝。此用例由替身记录 systemctl 调用。独立 Nginx HTTPS 实测上传 17 MiB 及整 128 MiB，超过端点限制返回 413；普通 API 保持 16 MiB 上限。备份脚本在 umask 022 时仍写入私有 0700 目录与 0600 文件。[安装器验收](../../scripts/release/verify-server-installer.py) · [网关验收](../../scripts/release/verify-linux-gateway.py)

1. 在企业自己的 GitHub App、模型端点和 OIDC IdP 上，分别从新建和导入两个入口跑通同一项需求，审查 PR、测试与制品间的来源证明。模拟模型与回环 GitHub 协议用于确定性回归。
2. 静态站点已在双机经真实中控签名发布。Java 订单服务在独立 x86_64 环境使用真实 systemd 用户单元，实测兼容扩展迁移、坏版本恢复、回退后读取前后订单并创建第三笔；该项发布指令来自 HTTPS 测试服务。下一步用真实中控对 Java 部署完成全链，补验持续流量、后台消费者交接及多节点滚动。业务签名私钥、环境密钥分发与外部模型凭据轮换由企业配置。
3. 恢复耗时是小样本实测值。PostgreSQL 按命名点恢复已有小样本证据。企业规模下的连续归档保留、任意时间点恢复、中间件多故障域拓扑、容量目标和对象存储共享仍需实测。
4. 在分别独立的中控主机、负载均衡器、共享制品存储与数据库故障域上，验证工作区连接路由、存量 Android 监控、调度和完整控制面恢复。节点 CPU、盘与内存观测不等同于多租户强隔离配额。
5. 当前编码节点从专用私有文件读取模型凭据。项目级中控模型网关及短时任务凭据仍待交付。核对真实上游许可、镜像、扩展和包内 licenses/audit.json；复核 Git 历史的环境标识与凭据。当前树中已将可识别的旧部署域名和主机别名改为示例，历史提交仍含旧值。公开仓库和签名发布应由维护者执行。

## 复现入口

- 运行 `node scripts/check-openapi.mjs`、两个仓库文档检查脚本、后端 `mvnw test`、Go vet/test、Worker 的 `npm test` 和 Android 单测、组装任务。
- 项目清单工具使用 `python -m pip install -r scripts/project/requirements.txt`。执行 `python scripts/project/project.py new /path/to/new-repo` 或 `inspect /path/to/existing-repo`，用 `validate` 校验源码根、依赖顺序、服务、配置与密钥引用。inspect 默认输出草案。
- 参考工程真实中间件回归用 `python3 examples/orders/verify_runtime.py /path/to/orders.jar`。需要 Linux、Java 21 和已准备脚本所列三个固定摘要的容器镜像。两机作业、签名发布和故障接管使用[验收脚本目录](../../scripts/api-test/README.md)。
