# 中控跨 JVM 作业接管验收

2026-11-12 在一台 x86_64 Linux 控制机和一台 ARM64 Linux 开发节点实测。控制机在专用临时目录中运行 MySQL Community Server 8.4.10，空库应用迁移至 V47。两个中控 JVM 使用 Java 21、同一专用数据库、相同 JWT 和加密密钥、不同回环监听端口。节点主动连接，使用非 root 身份、Git 固定基准和 bwrap 测试工作区。中控启用 `ENGINEERING_CLUSTER_CONNECTIONS`。本次为跨进程冷接管，控制机、MySQL 和两机网络保持可用。

1. 从用户 REST 登录、创建项目、注册开发节点、分配测试环境，并用同一请求标识两次提交仓库测试。项目只出现一个作业。
2. 测试在 ARM64 节点产生一个随机执行标记，真实退出码为 0。代理收到首个终态 ACK，暂停向节点确认。夹具从 MySQL 读取此时节点、所属中控实例和 WebSocket 会话，再对自己创建的第一个 JVM 发送 SIGKILL 并核验退出状态。
3. 夹具在另一端口启动第二个 JVM，先读取数据库确认旧连接归属在崩溃后得以保留，再切换 REST 及 WebSocket 目标。节点重新连接，旧登录 JWT 继续用于查询原作业。
4. 数据库的 server_id 保持一致，instance_id 和 session_id 都发生变化。同一作业所有终态重送内容一致，节点日志中只出现一次执行标记，原作业的三个日志分段、成功状态和退出码均可读。首次通过时观察到三次等值终态送达。完成后等待所有临时进程退出，远程检查两个独立目录均已删除。

第二次验收让代理在备用 JVM 尚未就绪时返回 HTTP 503，恢复后共建立两个有效 WebSocket 会话，观察到三次等值终态、一个随机执行标记和零退出码。两个临时目录再次完成清理。

随后以 Flyway V50 中控和新的 ARM64 Agent 合并执行 `--web-dist`、`--capture-build` 和 `--failover`。Edge 登录并发起真实测试，重启切换后重新进入同一作业读取成功报告。能力 API 返回 Linux/ARM64、正数 CPU、项目登记的 orders 仓库和 git、tar 工具。节点从固定提交生成 10,240 字节 static-tar；正式上传器的首次成功回执被丢弃，第二次上传获得原制品 ID，项目目录仅有一份制品。通过用户 API 下载核对 SHA-256、字节数、来源节点、runId、projectId、commitSha 和 tar 中的 `index.html`。该轮观测到两个有效 WebSocket 会话、三次等值终态、一个执行标记、三个日志分段和实际退出码 0，最后完成两台夹具的进程退出与目录清理。

在[双机验收程序](../../scripts/api-test/run-project-jobs-e2e.py)的常规参数后附加 `--failover` 即可复现。[测试说明](../../scripts/api-test/README.md)列明环境要求。验收用 JAR SHA-256 为 `489a962f6fec9ae1c8a30246ad69bec21d69e2d83ac51f0e98eaae80790e0e27`，ARM64 Agent SHA-256 为 `c4e9367120b4f6536ef5925911f2aa643ba6ddaa86a3e5d3ab5e8914efe06cbc`。
