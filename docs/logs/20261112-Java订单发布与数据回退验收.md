# Java 订单服务候选发布与数据回退验收

2026-11-12，在 x86_64 Linux 测试机上以新建的非登录普通用户运行正式发布执行器和两个 systemd 255 用户服务。Java 21 执行仓库订单项目构建的 Spring Boot JAR，三个独立容器提供 PostgreSQL、Redis 和 RabbitMQ。所有端口绑定回环。候选和活动实例使用不同数据库、Redis 逻辑库及 RabbitMQ vhost。测试用 HTTPS 接口提供固定的发布指令和制品，并记录执行器的真实回执。

| 发布操作 | 节点及业务结果 |
| --- | --- |
| 签名原版 JAR | 候选 `/api/orders` 返回订单列表，活动单元切换到相同字节，回执 `healthy`。创建第一笔订单。 |
| 签名带 V2 迁移的 JAR | Flyway 新增可空的 `fulfilment_note` 列，活动单元切换到新摘要，回执 `healthy`。创建第二笔订单并发货。 |
| 签名故障 JAR | 仅活动配置改变应用上下文路径。候选照常启动，活动业务探针失败，节点恢复上一健康 JAR 并返回 `failed`。 |
| 指定原版制品回滚 | 节点重新验签，候选和活动探针通过，回执 `healthy`。原版读取到第一笔待发货订单、第二笔已发货订单，能再创建及读取第三笔订单。 |

各次回执均已落入节点日志并获 HTTPS 确认。逐次比对活动目录 JAR 与预期制品摘要，确认活动单元为 `active`、候选单元为 `inactive`。最终 PostgreSQL 活动库 3 笔订单、4 个已发 Outbox 事件、4 个唯一消费回执，候选订单表 0 行，扩展列仍存在。Redis 中存在第二笔订单版本 2 的缓存。全程沿用同一个活动库，未从快照还原数据。

最终复测的原版 SHA-256 为 `746aa2a6f32bb7521784cbc5e436540ac4f5977f8142d2c60e6c109c0163a5f9`，V2 为 `487b1322b5a075282ef04cf56d90a7170468edf7b3f32e4393cdcb86f1a461a1`，故障包为 `0f9ab2f9e886a202e2f18faa8ec2985e4cbf0cadb5a263b1db13e4af30e629c5`。第三次回执明确记录切换失败并恢复，自动恢复后及显式回滚后分别核对了前两笔订单的完整 API 返回值。

首次运行发现 JVM 正常响应 SIGTERM 时返回退出码 143，临时用户单元将此记为失败。验收单元补充 `SuccessExitStatus=143` 后复跑。单元的启动钩子等待本机 TCP 开始监听，正式执行器随后访问业务端点判定候选和活动版本是否健康。

验收结束后已停止用户服务、用户管理器并移除独立容器、卷及临时目录。另一次只读检查发现 `userdel` 留下三次运行创建的空邮箱，逐个核对 useradd 日志、普通文件类型、原 UID 和大小后移除，并将该校验加入复跑脚本。再次独立检查，测试容器、账户、邮箱及目录的剩余数量均为零。

复跑入口和环境依赖见[订单回归工程](../../examples/orders/README.md)。本轮覆盖单机、单实例 Java 切换及可向后兼容的迁移。真实 Java 中控与跨机节点的制品来源、提升、终态回执已在[签名静态制品双机验收](20261112-签名静态制品发布双机验收.md)单独核验。Java 多节点滚动切换、持续流量下的可用性、不可逆迁移与整库恢复仍待独立验收。

## 后端模板独立构建复核

同日按用户选定的交付范围重新从工作区导出订单后端模板。两次导出相同的 14 个文件，ZIP 的 SHA-256 均为 `969f8711750f597222b5d73cd055e4738bf55a60513d9ae09339ab9c4edaa6ec`。使用项目 CLI 在空目录新建工程并运行清单校验，发布顺序包含 PostgreSQL、Redis、RabbitMQ 和 Spring Boot API。用 Java 21 执行 `mvn -o -B package`，全新工程成功生成 JAR，两个订单业务测试全部通过。对新建模板和存量客户端导入识别的两项回归均通过。构建临时目录已清理。
