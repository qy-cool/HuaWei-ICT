# 企业自托管平台后端技术栈与架构设计

本设计服务于三个交付对象：企业中控、Linux 工程节点、业务应用及其数据服务。前端框架由项目负责人另行选择。本轮后端以 REST、WebSocket、作业回执、制品、事件和 OpenAPI 供调用方接入。下文分别标记仓库已用的技术、需要完成的工程连接和需要企业提供的资源。

## 1. 软件装在哪里，谁能访问它

| 部署单元 | 进程与持久数据 | 网络方向、身份与故障边界 |
|---|---|---|
| 中控入口 | Nginx 终止 TLS，Java 服务监听内网或回环；独立的工作区会话代理按工作区配置 | 人用 HTTPS 和项目身份；Agent 主动 WSS。对工作区票据、制品上传和控制帧设置不同路由与限制。重启入口时已经部署的业务仍通过自己的业务网络运行 |
| 中控应用 | Java 21、Spring Boot、MySQL 元数据、制品目录、可选消息基础设施 | 中控知道项目和允许的目标。它保存任务、审批、发布代次和实际回执。服务端在读取、派发及执行敏感动作前检查授权 |
| 开发/构建节点 | Go Agent、Git 对象库、独立作业状态目录、只读工具链、构建输出；按需安装 Pi 和 code-server | 节点通过项目与环境分配获得可执行范围。测试代码运行在低权隔离目录。SSH 仅用于企业准备机器和可控联调；常规作业从节点主动连接的链路接单 |
| 应用节点 | 业务 JAR 或静态制品、版本目录、候选和活动实例、节点回执 | 使用节点身份拉取自身目标制品。核验来源、摘要和签名后启动候选；通过应用级探针再切换。节点状态与中控的发布意图分别记录 |
| 数据/缓存/消息节点 | PostgreSQL 业务库、Redis、RabbitMQ，各自独立账号、数据卷、备份目标 | 业务流量从应用节点直达。三种服务可以分机，首批实测也包含同机隔离实例。跨机验收需从应用身份实际读写，分别检查 DNS、端口、TLS、账号与服务权限 |
| 独立备份位置与身份源 | 企业保管的备份、解密材料、OIDC 身份源、GitHub App 以及模型端点 | 灾备包含密钥、数据库与制品内容。真实企业 GitHub 写入和模型调用由试点安装提供。正式签名密钥由维护者或企业独立保管 |

## 2. 工具和技术栈如何选

| 层 | 当前基线或计划 | 选择依据、代价及切换时机 |
|---|---|---|
| Java 中控 | 已用 JDK 21、Spring Boot 3.4.13、Maven Wrapper、MyBatis-Plus 3.5.12，工程模块也使用 Spring JDBC 与事务。版本以 POM 和 Wrapper 为准 | 现有身份、监控、告警和回归已在这套组合上运行。项目、作业、发布先保留模块化单体。在调度延迟、模型代理吞吐或工作区连接数说明需要时，按现有模块边界拆进程。[后端构建清单](../../server/pom.xml) |
| 平台数据 | 已用 MySQL 8.4 和 Flyway，原库 V1–V37，本轮 V38–V50。开发单测可用 H2，迁移和锁行为另在真实 MySQL 上验证 | MySQL 是项目授权、运行、审批与发布事实来源。业务侧可独立使用 PostgreSQL。迁移继续追加版本，演练从旧数据库升级和从空库恢复两条路径。[迁移清单](../../server/src/main/resources/db/migration) |
| 调度与实时状态 | Go 节点主动 WSS、作业标识、日志游标、终态确认和重放，MySQL 持久记录。原监控告警域使用 RabbitMQ Outbox | 节点能在 NAT 后上线。已持久终态可在断线后补交，未知外部效果进入“待核实”。工程作业和 RabbitMQ 通知域有各自的证据；若增消息唤醒，数据库扫描仍承担漏投恢复。[作业协议](../protocol/node-jobs-v1.md) |
| 节点与隔离 | Go module 声明 1.23；Linux 非 root、Git、bubblewrap、预先批准的测试命令和工具链。工作区单独使用可写持久卷 | Go 可以交叉编译 amd64/arm64。CPU 架构、内存、磁盘及工具链要作为调度输入。空间不足、用户命名空间不可用、进程树未回收、只读卷不可用分别触发明确的失败或能力降级。企业通用仓库构建还需单独核验配额与跨项目隔离。[Go 依赖](../../agent/go.mod) |
| 源码与 PR | 已有 GitHub App 的安装身份、仓库 ID、模板创建、分支、PR、签名 webhook；待补仓库到节点的自动同步 | 用仓库 ID 表示身份，用完整提交标识内容。分支是可移动引用。计划由中控在受权时解析 ref 到 SHA，节点取得本作业的短期读权限。同名仓库、重放 webhook、默认分支前移都应能单独复测。[GitHub 接入](../ops/github-app-repositories.md) |
| 编码与 Java 分析 | 已用 Node.js 24、锁定的 Pi SDK 1.4.0、受控读写和独立工作树。Java 查询使用固定 Maven 发布物内的 IntelliJ Java PSI；ZCode 提供交互参考 | 使用现成的会话、流式事件和取消能力，自研部分负责工具授权、审批、差异和审计。Java 查询服务进程能独立退出，失败时保留文本与编译器诊断。计划将模型调用移到项目级网关；当前开发节点的长期模型凭据仍由企业单独配置。[运行时](../../worker/README.md) · [Java 分析](../../worker/java-analysis/README.md) |

| 制品、签名与发布 | 当前是本地持久目录 + SHA-256，真实构建节点登记来源；OpenSSL 分离签名、HTTPS 下载，Linux 版本目录、systemd 用户单元、业务探针 | 测试和生产使用相同制品。数据库保存元数据，字节内容单独存储。单机安装简单，多个中控实例则需要一致的共享内容后端。S3 兼容适配器属于后续交付，要验证条件写入、读后校验、删除保留、权限和恢复。[发布执行器](../../deploy/release/README.md) |

## 3. 标识、权限和证据应怎样贯穿全程

一次订单需求首先关联项目、提出者和仓库身份。仓库绑定与具体节点的项目分配分别授权。选择分支时保存当时解析出的提交；开始 AI 任务时再固定模型、文件范围、用户模式和基准提交。开发者的个人工作树、AI 的写入目录与只读测试源码分别创建。发生冲突时保留双侧文件和各自基准，交给负责人解决。

PR 合并事件到达后，建议按投递 ID 去重，按实际合并提交创建构建运行。一次运行记录工作树来源、命令、工具链、真实退出码和报告引用。节点从隔离输出采集制品，再以节点身份登记作业 ID、提交和摘要。生产提升核对目标环境授权、同一服务测试回执和同一制品；应用节点下载后还要在本机验签。后续任务不得改变历史运行证据。

| 故障发生在什么边界 | 保存什么 | 恢复时怎样决定 |
|---|---|---|
| 中控写入与消息发送之间 | 数据库作业、请求幂等键、目标及参数 | 扫描待派发记录，用原 ID 继续；同一个 ID 带不同参数时反馈冲突 |
| 节点执行结束与中控确认之间 | 节点持久终态、日志序号、执行标记；中控持久化后再发确认 | 重连返回原结果。即使更换中控进程，同一执行仍只有一份事实记录 |
| 版本切换与结果落盘之间 | 实际活动版本、发布代次、业务探针及可核对的前一版本 | 证据充足时补写结果。不能判定效果时进入待核实，保留现场和负责人决策 |
| 应用回滚与数据迁移之间 | 迁移版本、变更是否向后兼容、回滚前后取样订单 | 先扩展数据库结构，后升级应用。回退应用时保留新订单；恢复整库走独立授权和单独业务核对 |
| 凭据撤销与正在执行的动作之间 | 作业主体、审批绑定的对象与期限、连接归属、最后确认步骤 | 拒绝新写入/派发，断开不再授权的会话；对已产生的外部效果单独核实，记录实际结果 |

## 4. 如何准备三种开发与验收环境

1. **本机单组件环境。** 安装 Java 21、Git、Go 工具链以及可选的 Node.js 24 编码运行时。中控使用 `server/mvnw`，节点使用 Go 模块，Pi 依赖按 npm lock 安装。此层覆盖资源授权、状态转换、幂等、SDK 事件和契约。运行记录标明操作系统与实际工具链。
2. **两台 Linux 机器的集成环境。** 一台中控配专用临时 MySQL、回环 HTTPS/WSS 网关和制品目录；另一台作为非 root 节点，准备 Git、bubblewrap、受信工具链与持久目录。两机先核对 CPU 架构、磁盘余量及业务网络。以固定提交测试、丢回执、重启中控、复核执行次数，再运行签名制品提升和坏版本回滚。控制面是否切换、业务环境是否同物理机要分别记录。
3. **企业试点与独立故障域。** 企业提供获批的 GitHub App 安装和测试仓库、可使用的模型端点、真实 OIDC 测试主体、测试域名和证书、独立应用与数据节点、备份解密材料。先用两个项目和不同角色验证隔离，再运行新建/导入两条需求。规模测试采用企业给定的并行作业、日志保留与恢复目标，实测后填写支持矩阵。

## 5. 哪些技术决定在什么时候做

| 决定 | 进入条件 | 判断证据与交付物 |
|---|---|---|
| Git 同步协议与凭据代理 | A1/A2 第一次设计评审 | 用新建和导入两类仓库、两个节点、分支前移与撤权构造用例。比较中控传输对象与节点短期直读的网络、存储、凭据风险，记录采用方式及断线续传策略 |
| 任务日志及大报告存储 | 作业能够导出多段日志、JUnit 等报告 | 用小报告与超过当前日志片段上限的真实构建各测一次。数据库留状态与索引，大对象按大小、权限、保留期单独设计；需要续读、截断和过期状态 |
| 模型网关与预算 | 企业试点需要多项目密钥和成本归属 | 同一用户对两个项目采用不同模型与源码白名单；撤权或超预算后观察下一次请求被阻止。记录提示、输出、令牌与审计的保留边界，只展示任务授权所需证据 |
| 制品共享与多实例接管 | 两个中控需同时服务或要求异机灾备 | 在第二个实例下载第一个实例接收的同摘要制品。停止源节点后，目标实例在恢复模式对账原作业与连接归属，实测 RTO 和业务数据恢复点 |
| 第二编码引擎及完整 IDE 索引 | 首个引擎的权限、预算、取消、恢复、差异、测试契约已能稳定复跑 | 候选引擎重复同一组许可与故障测试；大型多模块 Spring 工程测符号准确率、冷启动、峰值内存。把固定上游版本、实际分发范围及许可证登记后再调整支持清单 |
| 管理台前端 | 由负责人另行确定框架、开发节奏及界面负责人 | 后端提供版本化 OpenAPI、错误码、分页和日志续读示例、幂等及撤权语义。任何客户端可单独完成契约测试 |

具体工作包依赖、负责人建议和下一里程碑见[现状盘点与开发队列](20261112-现状盘点与下一轮开发计划.md)；长期工作量为原始全范围估算，各工作包以退出条件为准。[总体规划](20261112-企业自托管AI软件工程平台总体规划.md)

## 6. 容量、可观察性和长期维护

| 需要回答的问题 | 应采集的指标与关联字段 | 用什么结果做决定 |
|---|---|---|
| 加节点能解决排队吗 | 每项目排队深度、可用且满足架构/工具链的节点数、从入队到接单和接单到执行的时间分布，关联 project_id、job_id、server_id | 区分没有合适节点、调度延迟和构建本身耗时。先用一个固定负载逐步增加并发，再按饱和点扩开发节点或调中控 |
| 日志和制品会占多少空间 | 每次运行的日志字节、产物压缩后大小、每天构建次数、环境提升次数、去重后实际写入、保留天数 | 初估容量取每日新增字节乘保留天数，再加在传大文件、备份和恢复临时空间。用真实订单工程与较大导入项目校正；健康发布和待核实任务引用的对象不能提前清理 |
| 作业停在哪里 | 已接收/已执行/已确认的时间、连接实例、日志游标、上传确认、授权撤销、实际制品与发布代次 | 从一个运行号重建时间线，工程日志只保存允许的源码摘要和必要输出。区分节点掉线、代理超时、执行失败、探针失败和结果未知 |
| 服务恢复得多快、能恢复到哪里 | 分项计时发现、对账、下载、启动、业务探针；记录最近可恢复事务或实际恢复点与最后正常请求的距离 | 平台停机恢复的 RTO（恢复用时）和业务数据 RPO（可容忍的数据时间损失）分别测。小样本演练保留机器、数据量和版本，企业根据实际目标确定副本、容量和演练频率 |
| 升级是否兼容 | REST/协议版本、旧 Agent/Android 行为、迁移前后数据量及授权、相邻版本间作业和制品的重读结果 | 每次发行核对全新安装、旧库升级、从备份重建。被撤销的节点在升级后仍拒绝，未完成作业在恢复后对账。先编制实际支持矩阵，再承诺版本兼容窗口 |
