# A1–A5 后端接口与故障验收设计

规划日期 2026-11-12。本设计细化[近期工作包 A1–A5](20261112-现状盘点与下一轮开发计划.md)。本轮开发入口是 Java REST、Go 节点协议、Pi Worker 和企业安装脚本。管理台框架由项目负责人选定，任一受权 API 客户端均可参加验收。文中“建议新增”“建议扩展”的 API、状态、表和夹具均为待评审方案，正式行为以落地后的 OpenAPI、数据库迁移和实测报告为准。

**第一次可交付的结果**是企业只在测试节点准备一次账户、工具链和目录。以后添加项目时，从平台管理员绑定的仓库选择分支，通过 API 让原本没有该仓库的节点跑出第一份包含实际提交、退出码和节点身份的报告。第二个可交付结果是 GitHub 的实际合并提交能一路追溯到成功测试、节点生成的制品与运行中的版本。

## A1　按仓库 ID 解析并固定提交

**身份约定。** 首版继续支持每套中控配置一处 GitHub API 和一个 App installation。路径中的 `repositoryId` 使用现有 GitHub 数值型 `remote_id` 的十进制表示。中控从项目绑定和受信配置取得 installation、组织、允许的分支和远端地址。请求方只提供仓库 ID、ref 和可选期望 SHA。仓库名或节点别名允许变更；已创建快照持久记录原 ref、40 位小写完整 Git commit SHA、树 SHA、绑定代次、发起人和 UTC 解析时间。首版仅支持 Git SHA-1 仓库的 `refs/heads/…`，tag、任意提交表达式和短 SHA 的扩展另行设计。

以下表中的路径均为**建议新增**，共同前缀为 `/api/projects/{projectId}`。示例响应字段位于现有 API 响应信封的 `data` 中。建议新工程契约使用 camelCase，与旧作业接口已有的 snake_case 分开记录。

| 方法和相对路径 | 输入 | 成功输出及主要失败 |
|---|---|---|
| `PUT /repositories/{repositoryId}/source-policy` | 平台管理员发起，`{requestId,expectedPolicyVersion,allowedRefs}`。首次只接受显式完整分支引用，默认仅仓库当前默认分支。 | 返回 `{policyVersion,allowedRefs}`。比较并更新版本，禁止空白、通配符及非法 ref。缩小允许范围时，所有未开始或正在领取授权的操作重查，已解析快照保留历史来源。 |
| `GET /repositories/{repositoryId}/refs` | 可选不透明分页游标和条数上限 | `items[{ref,commitSha}],nextCursor`。查询者须有项目读取权限，结果限定当前绑定的允许分支。此响应是读时观察，分支可能在调用后前移。 |
| `POST /repositories/{repositoryId}/snapshots` | `{requestId,ref,expectedCommitSha?}`，需项目开发权限 | 返回 `{snapshotId,repositoryId,ref,commitSha,treeSha,bindingGeneration,resolvedAt}`。若提供的期望 SHA 与现场解析不符，返回冲突。调用者可重新读取并显式接受新提交。 |
| `GET /snapshots/{snapshotId}` | 路径 ID，需项目读取权限 | 返回原始来源及可否继续用于新操作。绑定已撤销时只对具有该项目历史记录读取权的人员提供审计元数据。另一个项目请求同一 ID 不暴露其所属仓库或 ref。 |

建议交互样例，数字为测试仓库和节点 ID，UUID 与 SHA 均为示意。

```json
{
  "requestId": "9d41136f-17ef-47f4-8fea-9a180e542777",
  "ref": "refs/heads/main",
  "expectedCommitSha": "0123456789abcdef0123456789abcdef01234567"
}
```

```json
{
  "snapshotId": "ccd72e50-70fc-4134-8366-d09f05635d9d",
  "repositoryId": 314,
  "ref": "refs/heads/main",
  "commitSha": "0123456789abcdef0123456789abcdef01234567",
  "treeSha": "76543210fedcba9876543210fedcba9876543210",
  "bindingGeneration": 4,
  "resolvedAt": "2026-11-12T09:00:00Z"
}
```

**并发与重试。** 建议以 `(项目,发起人,操作类型,requestId)` 唯一标识幂等请求，保存规范化业务字段的摘要及结果 ID。原请求响应丢失时返回原快照，即使该分支已经前移；同键不同请求返回冲突。并发创建共用唯一键和一次持久结果。访问上游前检查权限，提交持久结果前检查绑定代次仍然有效，远端网络等待期间不持有 MySQL 行锁。暂时失败可继续同一请求，客户端能通过错误语义区分网络暂不可用、分支不存在、期望 SHA 变化和无权限。未认证、无权操作、不可见对象、参数错误、版本冲突、上游暂不可用应分别映射至既有错误信封与明确 HTTP 状态；业务错误码在 OpenAPI 评审时分配。

**关系变更。** 仓库改名时用 GitHub 返回的稳定 ID 核对再更新名称。分支改名后保留旧快照的原 ref，新请求选择当前允许 ref。对删除绑定、安装撤销、重新绑定分配单调递增代次，旧能力和仍在队列的任务无法借新绑定继续。测试构造先后在两个项目授权的同一 remote ID，以及旧仓库改名后出现的同名新仓库；记录不应串联。V44 当前将 remote ID 唯一绑定一个项目，首版保留此约束。[现有 V44 数据定义](../../server/src/main/resources/db/migration/V44__project_github_repositories.sql)

## A2　把批准的源码同步到空节点

**建议首版传输。** 企业先建立受信 Git 出口。由受管同步进程按当前 GitHub installation 对指定仓库领取只读权限，用受信 HTTPS 和精确 ref 取得指定提交，在受保护的临时镜像中固定私有 ref，校验 commit 和 tree，生成可独立导入的 Git bundle。可从所选分支快进后的历史中取得旧快照；若强推、删分支或上游清理后无法证明固定提交来源，返回 `source_unavailable`，保留原快照供审计。同步进程需要先核对选中的 SHA 确属批准的分支。bundle 只包含该快照及其可达历史，要求项目具有读取该段仓库历史的授权。对仅授权部分文件的 Pi 任务，宿主在导出给 Worker 时仍按文件策略收窄。首批遇到 LFS 外部对象、子模块或超出大小/磁盘限额时，返回明确的不支持或容量结果。

| 建议新增接口或协议 | 身份与输入 | 可核验输出 |
|---|---|---|
| `POST /api/projects/{projectId}/source-syncs` | 项目开发者及以上，`{requestId,snapshotId,serverId}`。重查当前成员、仓库绑定和 dev/test 节点分配。 | `{syncId,snapshotId,serverId,state}`。仅新能力 `source.sync.v1` 可认领，旧 Agent 明确返回能力不匹配。 |
| `GET /api/projects/{projectId}/source-syncs/{syncId}` | 项目可读，按所属项目查询 | 状态、变更时刻、尝试次数、最后错误分类、已验证 commit/tree、bundle SHA-256、节点号。 |
| 建议在认证 WSS 增加独立同步动作及结果确认 | 下行含 `syncId,snapshotId,projectId,serverId,generation,commitSha,treeSha,bundleSha256,byteCount,deadline`；节点身份取自已认证连接。 | 节点持久记录接单，导入临时隔离目录，执行 Git 对象核验；安装、记录结果后上报。中控持久化后确认，重连回放。与现有 `job.execute` 独立协商。 |
| `POST /api/source-agent/syncs/{syncId}/grant` 和 `GET /api/source-agent/syncs/{syncId}/content` | 已认证的目标节点先领取绑定 sync、节点、绑定代次及有效期的短期下载授权。下载需同时出示节点凭据和短期授权，服务端每次请求重查撤权和期限。 | HTTPS 二进制内容支持按同一摘要复用已下载分段。响应携带已知长度和内容标识。日志只记授权 ID、时间与结果。长期 Git 密钥从企业密钥系统进入受管同步进程。 |

**状态转换。** `queued → preparing → transferring → verifying → ready`。可重试的网络中断保留同一 syncId、有效临时分段及重试上限，超时未完成进入 `failed`。取消和撤权先进入 `cancelling`，节点确认清理后进入 `cancelled`。节点已经安装但中控未收确认时，先核对该代次目录、commit/tree、持久回执，再决定是成功、已撤销还是 `uncertain`。业务不可用和历史技术事实分别保存，例如“已完成复制，授权已撤销”。已下载字节的回收由节点按项目密钥和缓存保留策略执行；撤权立即阻止凭旧授权取得新分段、启动新任务或打开工作区。

**原子安装与重放。** 节点以项目、repositoryId、snapshotId 分目录，在同一文件系统的临时目录完成校验和同步落盘，再原子更名为就绪对象。相同 syncId 和相同信封摘要重复送达直接查账；同 ID 换 SHA、目录或代次应记录冲突。局部失败后仅清理该操作拥有的临时目录。不同提交可并存，同一仓库不同项目的对象分开存储。安装结果由 `(节点,快照,绑定代次)` 唯一确认，受理、失败、确认重放均保留原请求的来源。

## A3　统一快照引用，隔离写入和权限

建议扩展现有三个资源。上线后先让旧客户端继续使用原字段，新增调用方只提交快照 ID。中控从快照解析 commit、仓库授权和实际节点，拒绝同时携带且互相矛盾的旧/新来源。已撤权或未同步到目标节点时，返回可定位的授权或同步状态，避免创建无法执行的成功记录。

| 资源 | 建议扩展的输入 | 状态、并发和验收 |
|---|---|---|
| 项目 `/runs` | 沿用现有 `request_id,server_id`，新增 `snapshot_id`。原 `repository,commit_sha` 路径保留。 | 新作业保存 snapshotId 与实际 checkout SHA，调用现有 v1 可靠作业语义。若需在节点带 snapshotId，使用已协商的新动作版本和固定结构。两份并发请求同键产生一个作业、一个测试标记。 |
| 项目 `/coding-tasks` | 沿用 task 请求幂等键、需求、模式和计划开关，新增 `snapshotId`。 | 宿主只向 Pi 工作树导出策略允许的文件。审批绑定基准 SHA、文件路径、新旧内容摘要和权限主体。候选修订产生新的摘要，须重新判定。任务租约失效时停止后续工具写入，已发生更改进入任务记录。模型仍由节点策略指定。 |
| 项目 `/workspaces` | 建议向新建的受管工作区增加 `snapshotId`。已有持久工作区换基线通过另一个显式操作，包含 `requestId,expectedGeneration,snapshotId`。 | 初始化时仅填充新建空卷。换基线应检查所有者、当前代次、Git 状态及未跟踪文件。非空或有未提交改动时返回可审查冲突或创建独立新工作卷。保留所有者原有工作树。节点继续以代次回报运行结果，已有票据、休眠恢复、撤权接口不变。 |

测试角色包含工作区所有者、同项目其他开发者和节点操作者。由所有者先编辑订单文件，Pi 在同一快照上改同一文件，同时让测试节点检出原快照。验收保存三份各自的文件摘要与差异，确认 Pi 撤权后无新增工具事件、旧工作区会话按权限状态断开、测试输出仍反映其实际检出的 SHA。若用户另有独立未撤销的身份授权，按资源逐项验证。客户端断开连接不取消后台作业，重新认证后仍从原游标取日志。[编码接口](../openapi/openapi-coding.json) · [作业协议](../protocol/node-jobs-v1.md)

## A4　把实际合并提交串到发布证据

1. 扩展现有已签名 webhook。先验 HMAC，再用 delivery UUID 和原文摘要去重。只接受本安装、仓库、目标分支和已登记 PR 的合并。接收与持久登记待处理事件同事务完成，外部 GitHub 查询在事务之外执行。查询 GitHub 的 PR 和目标提交核实真实合并 SHA，核对 remote ID、PR 编号、目标 ref 和 merged 状态，保存 PR 的 base、head 和最终合并 SHA。GitHub 暂未提供结果或提交尚不可见时进入 `awaiting_confirmation`，按上限重试并保留无法确认的原因。
2. 建议新增项目仓库下的 `PUT /repositories/{repositoryId}/merge-build-policy`，由平台管理员写入 `{requestId,expectedVersion,enabled,targetRef,serverId,service,executorId}`，返回策略 ID 和版本。executorId 指向在此项目具有开发权限、可单独撤销的执行身份，并记录授权它的管理员。首版可用企业专用且经审核的普通项目开发账号承载该身份，只允许在目标 dev/test 节点测试。管理员撤销策略、删除绑定、节点转入 prod 或构建身份失效后，调度重新校验并停止新任务。合并事件本身只触发重新测试和构建。环境提升继续由现有授权的项目负责人或生产平台管理员发起。
3. 同一 `(repositoryId,bindingGeneration,PR编号,实际合并SHA,构建策略版本)` 只有一个合并运行。即使两个不同 delivery UUID 指向同一合并，也只派发一次。先到的 merged 记录不会被后到的 open/closed 覆盖；若同一已合并 PR 的最终 SHA 有歧义，暂停并请求确认。历史合并事件迟到可以留下历史构建，自动发布或更新最新健康版本须重查当前环境代次。确需人工重测时分配新的 attempt，保存原因与操作者。
4. 复用 A1/A2 保存并送达**合并提交**，重用 A3 的节点测试和已有的节点上传器。测试失败留下真实输出；只有成功作业的同一节点才能登记该作业产生的构建字节。在签名、探针和授权满足后，将同一制品 ID 与 SHA-256 从测试提升生产。回滚沿用现有发布代次和节点结果。恢复应用时单独验证最新业务写入、消费者去重及数据库兼容。
5. 建议新增只读 `GET /api/projects/{projectId}/releases/{releaseId}/provenance`，返回 `releaseId,environment,service,nodeReceipts[],artifactId,artifactSha256,producerJobId,sourceNodeId,checkoutSha,snapshotId,repositoryId,pullNumber,mergeSha,taskId,testStatus`，并记录签名校验、探针及结果引用。测试/生产、自动回滚的各个节点分别列出实际活动版本。手工上传和历史作业缺失的关联返回空值和来源说明。无权项目不可读取上述任一子资源。

## 数据迁移、兼容和停用次序

以下为建议逻辑表和唯一约束。实施者在合并时按实际 Flyway 最新版本追加迁移，不改现有 V38–V50 脚本。旧库、全新安装和从备份恢复各跑一遍。

| 数据 | 建议增加的字段与约束 | 历史记录与撤销 |
|---|---|---|
| 仓库绑定代次、工程快照 | 增加不会因解绑而丢失的绑定历史，含 project、remote ID、installation、generation、active；快照引用该不可变历史行。快照另建按项目、提交与仓库检索的索引。 | 从 V44 现存活动行创建首代次，事务内验证项目归属。一条历史 PR 的同名仓库不能作为补写来源的依据。 |
| 幂等请求、节点同步 | 请求键和参数摘要唯一；同步表含节点、快照、代次、状态版本、截止时间及最后结果；节点回执按 syncId、节点和代次唯一。 | 权限撤销先停发能力，再保留历史证据。准备或损坏的临时分段按持有者和租约回收。定期扫描数据库补调漏掉的队列唤醒。 |
| 工作区、编码任务、作业 | 新增可空快照外键、来源类型和必要的基准字段；作业保留已有 `commit_sha`，以便老客户端查报告。 | 原有手工别名记录标为历史来源，仍可在原授权范围运行。若要绑定到新仓库，需管理员显式核对项目、remote ID 与可达 SHA。 |
| 合并运行、来源链 | 记录业务去重键、原交付 ID、可信执行身份、源任务和生成的作业 ID。发布查询复用 V42/V50 制品/发布表和节点来源。 | 不为历史包生成虚构的节点证明。外部 PR 状态、作业终态、制品收到及服务健康分别存储，原归属记录保留用于审计。 |

部署顺序建议为加表和可空字段 → 后端双读写 → 已协商能力的测试节点 → 单项目启用快照 → 放开试点。停用时用项目开关禁止创建新同步与合并任务，继续接收原作业回执和上传对账。降级前核对旧程序能否读取新增记录；在旧程序仅能按别名派发的环境，先排空快照作业，冻结自动调度。对生命周期已经开始但结果未知的作业保留现场。两个中控同时派发时由数据库租约和代次保护，旧持有者回来的写入不得覆盖较新终态。

## 故障注入与可核验输出

研发 CI 使用隔离 MySQL、临时 Git 仓库、可控 GitHub/模型 HTTP 服务和独立测试节点。代理在明确的消息或字节边界注入故障。各个等待有本地截止时间、状态诊断与清理路径。报告记录是否使用替身及其能覆盖的行为。

| 用例 | 注入点与操作者 | 要观察到的输出 |
|---|---|---|
| A1-01 分支前移 | 开发者读 ref 得到 X，Git 夹具在创建快照前把它移到 Y，以 `expectedCommitSha=X` 请求 | 冲突响应含客户端可处理的原因；已成功钉住的旧快照重试仍返回 X。 |
| A1-02 跨项目、解绑重绑 | 用项目 B 的 token 查询 A 的 ID；随后管理员解绑并将仓库授权给另一个项目 | 跨项目响应不含 repo/ref/成员详情。旧代次不能启动新的作业，即使显示名称相同。 |
| A2-01 半包与凭据过期 | 在下载到固定偏移量时断链，使授权过期，重连后申请新授权 | 同一 syncId 续传或重新下载；仅一个 ready 目录。对中控与节点分别核对 commit、tree、bundle SHA-256、长度。日志和测试环境不含令牌。 |
| A2-02 丢确认与错误节点 | 节点完成本地安装后丢首个确认；保存终态前后分别杀掉测试进程；第二节点提交第一节点的回执 | 身份不符被拒，原节点可重放；重复结果的安装标记只有一次。证据不足进入待核实，错误节点无法认领。 |
| A2-03 空间不足或损坏 | 给测试私有卷设置容量上限，或只改变传输中的一个字节 | 返回容量或摘要失败。没有可执行的半成品，原 ready 快照仍可读取。清理临时对象后明确重试操作与返回值。 |
| A3-01 并发编辑与撤权 | 人和 Pi 各自改同一文件，在审批请求后改目标内容或撤去开发权 | 原审批无法批准新字节；两个工作树保留各自内容。停用已有工作区访问，旧连接收到关闭，随后使用原会话再请求被拒。 |
| A4-01 重复、乱序与中控崩溃 | 同一合并换两个 delivery ID；先收 merged 后收旧 open；在保存合并记录后、派发前关闭测试 JVM | 一个合并运行和一个对应的测试作业。重启后从数据库接续原运行，持久的 mergeSha 未回退。 |
| A4-02 失败测试与错误制品 | 合并后故意让测试退出非零，另一个节点尝试为此作业上传；健康包首次成功上传回执另行丢弃 | 失败运行保留退出码和日志，无法取得生产制品资格；健康包按同一作业重试只有一个制品 ID 和摘要。 |
| A4-03 生产回滚与数据 | 在同一制品完成测试提升后发布探针失败的候选版；发布前后分别创建订单 | 真实活动版本、事件、生产认可的来源、回滚代次均可反查。旧订单与发布后新订单可从业务接口读取，重复消息未产生多条业务效果。 |
| A5-01 两个项目权限矩阵 | 分别用 A 的 viewer、developer、owner、平台管理员，B 的已审核用户和另一个节点身份请求日志、制品、IDE、PR、生产操作 | 保存脱敏操作、资源归属、实际 HTTP/业务码和是否出现副作用。A viewer 可查授权报告，B 用户读不到 A 的内容；普通开发者无法生产提升。 |

**建议实施后的断言命令。** 下例为 A2 的节点验收构想，路径和期望值由测试夹具生成。第一处目录是测试节点导入的 bare Git 对象库，第二处文件是中控包传输完成后的私有暂存副本。脚本在无访问令牌的校验子进程内运行，保留退出码和计算结果。

```sh
set -eu
actual_commit=$(git --git-dir="$TEST_OBJECTS" rev-parse --verify "$EXPECTED_COMMIT^{commit}")
actual_tree=$(git --git-dir="$TEST_OBJECTS" rev-parse --verify "$EXPECTED_COMMIT^{tree}")
test "$actual_commit" = "$EXPECTED_COMMIT"
test "$actual_tree" = "$EXPECTED_TREE"
actual_bundle=$(sha256sum "$TEST_BUNDLE" | cut -d ' ' -f 1)
test "$actual_bundle" = "$EXPECTED_BUNDLE_SHA256"
printf 'commit=%s\ntree=%s\nbundle=%s\n' "$actual_commit" "$actual_tree" "$actual_bundle"
```

**建议实施后的 API 验收顺序。** 用 A 的开发者会话执行 `GET refs → POST snapshot → POST source-sync → GET sync`，待节点确认后，以 `snapshot_id` 调用项目的 `POST /runs`，再读取该作业的详情和 `/logs?after=0`。将首次 `POST` 的请求 ID 原样重送并核对资源 ID，再用相同键、不同业务字段断言冲突。最后通过只读项目 B 会话重复访问 A 的资源。API 测试脚本应从去标识的输入配置获取企业域名和凭据，输出只包含响应业务码、资源 ID、状态、摘要和实测时点。

## A5　两种入口的交付和企业签收

| 入口 | 初始条件与差异检查 | 两条路径共用的最终断言 |
|---|---|---|
| 从企业模板新建 | 项目 A、空源码缓存、企业已批准的模板。重复创建请求产生一个私有远端仓库，确认仓库 ID、默认分支、模板基准及实际项目清单。 | 发起订单功能改动、取得人工审批，通过真实 PR 合并。取合并提交的节点测试、制品和测试/生产健康回执，反查同一需求。 |
| 导入已有仓库 | 项目 B、空源码缓存、组织已授权的存量仓库。保留既有分支、提交历史与业务文件。模块不能可靠识别时由项目负责人明确源码目录和受控测试入口，保存确认后的配置。 | 使用与 A 相同的业务断言及报告字段。两项目中同名服务、文件和仓库别名均按稳定 ID 和项目归属区分。 |

建议两仓库均从“订单允许创建和发货，尚待增加取消功能”的指定基线运行，先证明新增取消需求对应的红测会失败，再让 Pi 修改。当前订单参考工程已含取消能力；试点夹具须另备可追溯的起始提交，或选取新的、两仓库都未实现的需求。测试与生产证据核对已发货订单拒绝取消、重复请求幂等、缓存状态和消息去重，取证中标明新增测试和既存回归。

**企业验收的分工。** 安装方管理员提供专用 GitHub App、允许操作的组织、私有模板和可清理的试点仓库，授权新建/导入、PR 和 webhook；运维提供受管节点、可信签名、制品存储、隔离的数据环境与访问映射；模型管理员提供试点模型、源码范围和预算；业务负责人验证订单行为与回滚后的新旧数据。测试人员用同一脚本切换两类工程入口，每类独立记录原需求、操作人和模式、snapshotId、实际 mergeSha、jobId、退出码、报告和制品摘要、节点回执、模型标识、用量、实际计费或企业计价依据以及人工介入点。企业凭据故障或预算不足时保留已完成的证据，并单独报告尚待试点的用例。
