## 3. 下一次要交付给开发者的操作

**让调用方通过 API 选择已绑定的仓库和提交，把一台尚无该项目源码的受管节点接进来，直接跑出第一份有实际提交、测试和制品来源的报告。** 当前两机验收中，节点管理员事先准备了 Git 对象库；首次接入工作区还要准备持久目录、工具链和访问映射。这些现场步骤决定了现有能力能否让第二个项目、第二个团队重复使用。

| 工序 | 平台已有 | 需要接通的地方 |
|---|---|---|
| 从新项目模板或存量仓库开始 | 中控保存授权安装和具体仓库标识；按仓库 ID 解析选定分支并钉住为完整提交快照（V51）；受管同步进程把快照对象分发到声明能力的空节点（V53） | 让工作区、Pi 编码与测试作业引用同一快照基线（A3） |
| 人和 AI 同时改订单工程 | 手工配置的工作区、编码任务及测试节点均能工作 | 三者引用同一基准提交，各自保留可写目录。明确用户未提交改动、远端分支前移及冲突的处理 |
| 审查、合并、测试与发布 | 已有 PR 接口、事件去重、测试、构建来源及发布代次 | 将实际合并 SHA 绑定到重新测试和构建的运行；从发布页反查此次 PR 与需求 |
| 发布后处理告警或恢复数据 | 已有告警关联、回滚和单项备份恢复工具 | 将恢复请求、授权、节点动作、校验结果和原告警串为可审计的工程记录 |

## 4. 可直接进入开发队列的工作包

表中的负责人是建议分工，一人可兼任。按依赖安排，不预设团队人数或日期。

| 顺序 | 工作包及建议负责人 | 输入与依赖 | 可审查交付物和完成条件 |
|---|---|---|---|
| A1 · P0 | 仓库身份与提交选择（已完成 2026-11-16，见[代次与快照笔记](../../.agents/notes/implemented/architecture/2026-11-12-repository-binding-generations.md)）。中控、接口维护者 | 现有项目授权、GitHub 安装绑定和节点分配 | 仓库列表展示允许访问的来源。选定分支后记录仓库 ID、ref 及完整 SHA；同名仓库、分支改名、仓库撤权有一义的结果。客户端提交其他项目仓库时服务端拒绝 |
| A2 · P0 | 节点同步固定源码（回环夹具验证完成 2026-11-18，双机真实验收待做，见[同步路线笔记](../../.agents/notes/proposed/architecture/2026-11-18-node-source-sync.md)）。Agent、中控 | A1，可靠作业协议，企业网络与信任的 Git 出口 | 空节点按项目取回批准的提交，证明实际对象 SHA 与授权相符。中途断网后恢复，重复请求只生成一个有效结果。节点领用的短期读权限可撤销，持久日志和工作区都查不到长期密钥 |
| A3 · P0 | 工作区、Pi、测试使用同一基线。接口维护者、节点运行时 | A2，已有 code-server、Pi 及受限执行器 | 通过项目 API 获取工作区、取得短时访问权并执行测试。人和 AI 同时修改订单文件，保留两份差异；目标分支前移时显示冲突或新旧基线。关闭浏览器后作业仍然可对账，撤权后原 IDE 会话关闭 |
| A4 · P0 | 真实合并触发重测、出包与环境提升。仓库集成、发布 | A2、A3，现有 webhook 去重与 V50 来源 | 合并后记录实际合并 SHA；重复和乱序投递不会重复构建或覆盖新结果。保留失败测试，成功才生成该次运行的制品。测试与生产比较同一摘要，坏版本回滚。从运行节点可反查需求、PR、测试与制品 |
| A5 · P0 | 两种团队入口与越权回归。测试、企业试点负责人 | A1–A4，独立试点组织、两个项目与角色、企业模型端点 | “从模板新建”和“导入已有工程”各完成一次订单需求，进入真正的 GitHub PR 并合并。记录模型、审批、费用和实际结果。用 B 项目账号验证作业日志、制品、IDE 和生产发布均遵守 A 的权限 |
| B1 · P1 | 编码模型统一出口。中控、编码运行时 | 可与 A1 并行设计，接入 A5 前明确试点凭据部署 | 从节点私有模型凭据逐步过渡到中控按项目代理；单个任务可独立过期，不能改变模型目标或扩大源码范围。用模拟端点实测预算耗尽、轮换、取消、断线续看，再用企业端点复验 |
| B2 · P1 | 中间件备份与恢复接入中控。运维、Agent、中控 | 既有单项恢复工具、项目授权、可对账作业；先接 PostgreSQL | API 分别返回“备份已生成”和“已恢复并核验”。丢回执只做一次实际恢复。恢复点前订单保留、点后订单排除、源库可继续读写；Redis 随后核对 TTL，RabbitMQ 分别核对拓扑及业务消息 |
| C1 · P1 | 跨故障域恢复。平台运维 | 独立恢复主机、数据库、共享或可恢复的制品、独立保管的密钥 | 源中控不可用时在干净机器恢复，先对账未确认作业及撤销记录，再开放派发。检查节点重新认领、已部署版本、工作区访问。记录拓扑、数据量、停机时间和实际恢复点 |
| C2 · P2 | 企业稳定发行。维护者、发行工程 | A5、发布安全与支持矩阵、B2 与 C1 的实测记录 | 用可追溯源码构建 amd64/arm64 归档并检查 SBOM 与许可遗漏。完成干净安装、上一受支持版本升级、恢复到新机三条路径，核对签名及安装文档后由维护者发布 |

建议首先评审 **A1、A2 的契约与 A5 的验收用例**，让后端、后续客户端与验收人员使用同一仓库 ID、提交和作业身份。项目已有的单项测试继续保留为回归；备份界面、多实例共享存储和第二编码引擎各自按依赖排队。

### 首批可独立评审的改动

| 顺序 | 评审对象 | 合入前需回答的问题 |
|---|---|---|
| 第一批 | 仓库绑定、提交解析和越权的 API 契约；两个项目、同名仓库和两种用户角色的固定测试数据 | 服务端按哪个身份确定授权？分支被移动后如何找回原提交？对无权仓库是否暴露其他项目的存在？接口语义、审计字段、错误和复跑断言能否一一对应？ |
| 第二批 | 节点作业领取受控源码、持久同步记录、失败重试和撤权。保持老 Agent 与旧仓库配置兼容 | 一台空节点需要哪些工具、盘和网络？同步中断后复用哪些已校验对象？节点是否能证明实际执行的 SHA？旧节点不支持新动作时调度器如何反馈？ |
| 第三批 | 工作区、Pi 任务与测试作业引用同一源码记录，关联用户改动和测试报告 | 修改了同一文件时两份差异是否都能找回？取消后留下什么？PR 合并提交与建任务时基准不同时，哪次测试才可以出包？ |

第一批和第二批完成即可用两个 API 客户端和一台空节点独立验收。第三批通过以后再使用真实企业安装运行 A5。功能负责人每次附上契约差异、迁移策略、证据位置、失败时的恢复动作。原路线的 69–117 人周为全范围估算；已验证的工具和接口作为存量复用，各工作包在契约冻结后重新估算剩余量。
