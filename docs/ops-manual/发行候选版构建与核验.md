# 自托管发行候选版

每个 Linux 架构的后端候选包包含 Java 中控 JAR、Go Agent、工作区会话代理、Pi 编码 Worker 源码和 npm 锁文件、Spring Boot 订单 API 示例源码及测试，以及节点部署与数据恢复工具。客户端由企业或项目维护者自行选型，使用包内的 REST、WebSocket 契约接入。工作区需要的 code-server 可由企业独立部署。[API 契约](../openapi/README.md) · [节点协议](../protocol/node-jobs-v1.md) · [Worker 安装](../../worker/README.md)

## 从源码构建后端

发行工作流使用 Java 21、Go、Node.js 24 和 Python 3.11+。在仓库根目录准备对应工具后可以逐项检查。Node.js 用于编码 Worker、验收夹具和契约校验。

```sh
(cd server && bash mvnw -B -ntp package)
(cd agent && go vet ./... && go test ./...)
(cd deploy/workspace/session-guard && go test ./...)
(cd worker && npm ci && npm test)
(cd examples/orders/api && mvn -B -ntp verify)
node scripts/check-openapi.mjs
```

工作流针对 amd64、arm64 分别交叉编译节点和会话代理，然后调用 `scripts/release/build-kit.py`。归档附可提取的 JVM 与 Go 依赖许可证。维护者应复核 `licenses/audit.json` 中缺少内嵌许可文本的依赖以及单独安装的运行时。构建完成后生成 CycloneDX 软件物料清单及 GitHub 构建来源证明。

从解压后的包根目录，可以在独立 Python 环境安装 `scripts/project/requirements.txt`，运行以下命令检验所附模板。第一条创建一个新的订单后端样例，第二条验证源码目录、服务依赖及部署清单。

```sh
python3 scripts/project/project.py new ../orders-test
python3 scripts/project/project.py validate ../orders-test
```

## 验证下载内容

下载两个归档和 SHA256SUMS 后，在同一目录运行 `sha256sum -c SHA256SUMS`。随后对目标归档及 cloide.cdx.json 分别执行 `gh attestation verify FILE --repo OWNER/REPOSITORY`，使用你认可的上游仓库名。下载的包名与运行机器架构应相符。GitHub 的 attestations 页面可核对签名所对应的工作流和源码提交。[官方构建证明文档](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)

## 安装与升级

- 中控配合 Java 21、MySQL 与 HTTPS 网关。包中的 deploy/server/install.sh 按版本将 JAR 安装到 releases 目录。首次安装先落地 JAR、单元及私有环境文件，保留占位值时提示填写后手动启动。发行标识默认取 JAR 摘要；同一标识已指向其他字节时安装器拒绝覆盖。升级前先备份数据库、企业密钥材料和制品目录，核对源版本、Flyway 迁移、磁盘余量与可恢复副本。
- 中控 HTTPS 入口转发 `/api` 和节点长连接，两个制品上传接口允许 128 MiB，其他 API 默认限制 16 MiB。独立工作区使用专属域名和短时凭据，前端可以依据工作区契约申请访问。[中控部署](../../deploy/server/README.md) · [工作区手册](../../deploy/workspace/README.md)
- 原监控节点可使用 deploy/agent/install.sh 按机器架构选择二进制。开发节点使用独立的 cloide-build 用户和 deploy/agent/cloide-build-agent.service，组装只读工具链，安装私有状态目录与配置文件，参考[节点作业协议](../protocol/node-jobs-v1.md)。两种角色应分别登记身份。
- 工程模块恢复时先在隔离入口设置 ENGINEERING_RECOVERY_MODE=true，该模式暂停新测试派发、编码认领和发布分发，仍能接收终态。检查作业、制品、密钥与节点实际状态，再重新启用派发。

## 发布记录

工作流手动运行时保存构建材料。推送版本标签时创建 GitHub Release 草稿。维护者填写经过实测的安装、升级、恢复拓扑，复核许可证、已知限制、SBOM 和签名，再发布稳定版。本地组包证明源与二进制可组合；GitHub 签名和草稿发布须在配置好的 GitHub 仓库运行工作流后核验。[GitHub CLI 草稿发行选项](https://cli.github.com/manual/gh_release_create)
