# 单实例恢复验收记录

2026-11-12 使用两个独立故障域中的测试资源。x86_64 使用 Docker Engine 29.3.1、Compose v2.28.1，业务端口未发布。每轮从新的源实例备份并停止源服务，目标使用全新的 UUID、网络、容器、卷和业务密码。时间从开始恢复计至完成脚本的业务核验。

| 平台与模板 | 数据和核验 | 备份大小 | 恢复耗时 |
|---|---|---:|---:|
| x86_64 PostgreSQL | 两笔状态不同的订单，主键和 CHECK 约束均存在。非超级用户携新密码通过 TCP 读取记录，并在事务内写入、更新和回滚 | 1,949 B | 5.33 秒 |
| x86_64 PostgreSQL 18.6 物理恢复 | 基础备份完成后提交订单 301，创建命名点，再提交订单 302 并归档后一个点。目标精确重放到第一处 LSN，恢复后只含 301；目标新写 303，源仍含 301、302 | `pg_verifybackup` 校验完整物理备份；目标 WAL 段通过 SHA-256 | 15.61 秒 |
| x86_64 Redis 持久型 | 一笔带 TTL 的订单键。新实例加载 RDB、重建 AOF、重启后，携新 ACL 密码读取得到原值，剩余 TTL 在约定范围内 | 241 B | 9.51 秒 |
| x86_64 Redis 缓存型 | 源实例含订单缓存。目标冷启动为零个键，用新 ACL 密码写入权威样本并读取 | 65 B 策略清单 | 4.77 秒 |
| x86_64 RabbitMQ | 恢复 orders vhost 的交换机、队列、绑定和死信参数。源实例的一条待处理消息没有出现在目标；按同一业务 ID 两次重放，核对 requeue、redelivered 和消费确认 | 1,105 B | 14.57 秒 |
| ARM64 RabbitMQ 3.9.10 | 盒子自带软件包，两个独立节点名和数据目录，逐个启动。只启用回环网卡的独立网络、PID 命名空间、临时数据文件系统、非特权身份。恢复拓扑并核对三个事件、两个不同业务 ID、重投标记和最终空队列 | 单 vhost definitions | 10.09 秒 |

每轮 Docker 演练结束均依照本次 UUID 标签复查，容器、网络及卷均已清除。ARM 演练的宿主机业务配置和数据目录没有挂入命名空间；结束后复核临时 UID 下无进程，两个机器上的专属脚本目录均已移除。[Docker 演练入口](smoke.py) · [隔离 Linux 软件包演练入口](native_rabbit_drill.py)

物理恢复验收使用上表 PostgreSQL 镜像。最后一次基础备份 ID 为 `579bcef3-a2cf-4015-bd97-a5ce04359ee2`，备份结束 LSN 为 `0/3000120`。命名点 `after_payment_7a4be4b074ea4619` 及目标实例实际重放 LSN 均为 `0/40071E0`。源已将第二笔事务之后的 `0/5000140` 归档，恢复目标仍准确排除第二笔事务。实测拓扑为同一 Linux 节点的两个专属 Docker 网络和卷，覆盖单集群默认表空间布局与命名恢复点。[物理恢复演练入口](pitr_smoke.py)

以上耗时来自少量样本，业务规模 RTO/RPO、跨机自动切换、完整消息存储还原及应用层事务去重仍需按实际业务数据量验证。
